# 6.18 display bring-up on Fairphone 2 — findings, dead ends and resume points

**Status: parked 2026-07-31** in favour of a 6.12 LTS baseline (same projected
EOL, Dec 2028, with drm/msm's vram carveout still present). This document is the
resume point: everything below was established on-device this session and must
not be re-derived. Ledger entries: `dvfs-campaign-ledger.md` SES2-C/D.

---

## 1. One-paragraph summary

On 6.18 the FP2 panel can be brought fully to life (initialised, backlit, TE
pulsing, DSI at 1080p rates, MDP5 committing and completing frames, IOMMU
attached with vendor-identical context-bank state, zero faults) and **still show
nothing**. Separately, `simpledrm` on lk2nd's own framebuffer **does put pixels
on the panel** — but with visual glitches and a boot loop. Since simpledrm
involves neither drm/msm nor any IOMMU, the common factor in every failure is
**active display traffic on 6.18**, not the IOMMU port. That is the thread to
pull next time.

## 2. What was fixed (all committed, all real, all reusable)

Branches (pushed to origin):

| Branch | Contents |
|---|---|
| `6.18/topic/fp2-panel` | generated OTM1902B/S6D6FA1 panel drivers + FP2 display DT; TE enable; panel supply rails |
| `6.18/topic/mdp-iommu` | msm8974 qcom-iommu work adapted for the TZ-managed MDP instance: secure-gating fixes, V7S page tables, vendor BFB block, MDP5 snapshot hook, a DEBUG CB-state dump |
| `6.18/topic/display-carveout` | **empty except the MDP5 snapshot hook** — the carveout revert was attempted and abandoned (see §5) |
| `6.18/baseline` (`12bc65022c87`) | v6.18.41 + adsp-sensors + panel + smd-rpm-clocks + mmcc fix + mdp-iommu |

Root causes found, each from the vendor tree or the live oracle:

1. **Panel never ported.** `fairphone,fp2-panel` DT node and its drivers are
   out-of-tree in msm8974-mainline. **Use the `qcom-msm8974-6.16.y`
   regeneration** — the 6.15 drivers use `mipi_dsi_generic_write_seq()` /
   `mipi_dsi_dcs_write_seq()`, removed in favour of the `*_multi` API.
2. **Display controller deferred forever.** `qnoc-msm8974` interconnect
   providers fail probe with `-ENOENT` unless the msm8974 **RPM bus clocks** are
   re-added (`6.18/topic/smd-rpm-clocks`); the display controller then waits on
   MMSSNOC for ever ("deferred probe pending: supplier fc380000.interconnect").
3. **`mmss_s0_axi_clk` "stuck at off"** hangs the boot at display init; fixed by
   reparenting to `mmss_mmssnoc_axi_clk` with `CLK_SET_RATE_PARENT |
   CLK_OPS_PARENT_ENABLE` (vendor lineage `e604a98f5daf`).
4. **TE was never enabled** — and this is the class of bug to expect again: the
   vendor's `set_tear_on` (DCS 0x35) is **injected by the downstream mdss
   framework** from `qcom,mdss-dsi-te-dcs-command = <1>`, so it appears in no
   panel command blob and therefore in no generated driver. Without it MDP5's
   ping-pong never completes (`pp done time out, lm=0`) and nothing transfers.
5. **Panel rails unclaimed** by the panel driver (`vdd` = pm8941 l22 3.0 V,
   `vddio` = l12 1.8 V per `msm8974-mdss.dtsi`).
6. **Wrong page-table format.** The vendor programs **ARMv7 short-descriptor**
   (`TTBCR=0`, PRRR/NMRR) on *every* 8974 MMSS SMMU; mainline's qcom-iommu uses
   LPAE. With LPAE the bank "translates" garbage: no fault, black scanout, and
   occasional fetches into protected DDR (a plausible silent-reset mechanism).
   Fix: `ARM_V7S` for the secure msm8974 instance (TTBR0 32-bit, ASID in
   `CONTEXTIDR`). **Verified on-device**: `SCTLR=000010eb TCR=0 FSR=0`.
7. **Vendor BFB block never programmed** — 18 implementation-defined globals at
   `SMMU+0x2008..0x2540`, which downstream programs on every 8974 SMMU
   *including TZ-managed ones* ("bfb settings are always programmed by HLOS").
   Now carried in `qcom,iommu-bfb-regs/-data` and written after
   `restore_sec_cfg` ("programmed 18 BFB registers" at boot).
8. **The fork's IOMMU port broke secure instances.** It keyed three IP quirks
   *and* the TrustZone gate on `nonsecure`: `restore_sec_cfg()` was gated on a
   `-sec` **child** existing, so an instance with only non-secure banks (exactly
   the MDP shape: `secure-id 1` + one `-ns` bank) silently skipped the call that
   installs SMR/S2CR/CBAR — traffic then bypasses translation with raw physical
   addresses. Also re-keyed: the fatal `CB+0x10` (TCR2) write, `SCTLR.AFFD` vs
   `AFE`, and the `SMMU+0x2000` write (which on 8974 is `MICRO_MMU_CTRL`, not
   `SMMU_INTR_SEL_NS` — writing `0xffffffff` there boot-loops the SoC). Same
   audit fixes a latent `restore_sec_cfg` skip for msm8916/8939/8917 `gpu_iommu`.

## 3. Verified state of the failing configuration

With everything above applied (`6.18/baseline` = `12bc65022c87`):

- panel: probes, backlight DCS answers, TE pulses;
- DSI: `dsi0_ctrl` register dump matches the live oracle's working controller
  (only DMA_BASE/DMA_LEN differ — last-command state);
- MDP5: `plane-0 → CRTC[83]` commit + `flush=00000840` every ~30 ms, `pp done`
  timeouts stop after the TE fix;
- IOMMU: attached, `restore_sec_cfg` succeeds, BFB programmed, **zero context
  faults ever**;
- **screen: black.** 8 MB of `/dev/urandom` written into `/dev/fb0` changes
  nothing on the glass ⇒ the panel is not displaying our framebuffer at all
  (black, not garbage: no plausible "wrong mapping" signature).
- second failure: with the display enabled, **WCNSS bring-up (t≈8.3 s) triggers
  a silent reset / boot loop**. A WCNSS-firmware-removed variant boots stable
  (still black) — so the two failures are independent.

## 4. simpledrm — the promising start to resume from

`CONFIG_DRM_SIMPLEDRM=y` + the **headless** DTB (so drm/msm never touches the
panel) + lk2nd handing over its live framebuffer:

```
lk2nd.pass-simplefb=autorefresh,relocate,xrgb8888
clk_ignore_unused regulator_ignore_unused
```

- lk2nd (`lk2nd/display/simplefb.c`, `LK2ND_DISPLAY_CONT_SPLASH=1` in our build)
  creates `/chosen/framebuffer@<base>` (`compatible = "simple-framebuffer"`,
  reg/width/height/stride/format) plus a `no-map` `/reserved-memory` region, and
  `autorefresh` leaves MDP scanning the buffer out autonomously — required for a
  command-mode panel, otherwise nothing triggers a transfer.
- `clk_ignore_unused` / `regulator_ignore_unused` are mandatory: the kernel
  otherwise switches off the MDSS clocks and panel rails it sees no consumer
  for, killing lk2nd's scanout seconds into boot.
- **Result: pixels appeared on the panel** (first time on 6.18) — with visual
  glitches, and the image boot-loops.
- Variant kept as `configs/fairphone2_simplefb_defconfig` +
  `board/fairphone2/overlay-simplefb/` in the buildroot external tree.

Next steps for this path: check `stride`/`format` agreement between lk2nd and
simpledrm (glitches), and treat the boot loop as the §6 hypothesis below.

## 5. Dead ends — do not repeat

- **Reverting the carveout removal.** `eab7766c79fd` was removed *because
  msm8974 was its only user* and it blocked drm_gpuvm/VM_BIND (Rob Clark:
  "Maybe we can add support back in later, but I'm doubtful"), and
  `c94fc6d35685` then made no-IOMMU KMS a hard `-ENODEV` as a consequence of the
  GPUVM conversion. Reverse-applying conflicts in **every** touched file
  (`msm_drv.c`, `msm_drv.h`, `msm_gem.c`, `msm_gem.h`, `msm_kms.c`, plus
  a5xx/a6xx/adreno) because 6.18's VM_BIND rework moved all of it. It is a
  permanent fight with upstream churn, not a one-time port.
- **Debugging from the mainline side.** Hours went into mainline theories before
  the vendor tree was read; items 4 and 6 above were each ~30 lines of vendor
  source. The wall protocol added to `BLUEPRINT-kernel-feature-bringup.md` §6.1
  exists because of this session.

## 6. The hypothesis to test first next time

**Active display traffic destabilises this SoC on 6.18, independently of the
IOMMU.** Evidence: the reset/boot-loop appears with (a) drm/msm + MDP SMMU
translation, (b) drm/msm + BFB programmed, and (c) **simpledrm with no drm/msm
and no IOMMU at all** — while the identical hardware ran display for months on
6.12/6.16. Candidates, cheapest first:

1. **Bus/QoS programming** the vendor does and mainline does not (BIMC/MMSS
   QoS, MDP client priorities) — the display is the only hard-real-time master
   on this SoC and it shares BIMC with WCNSS's boot traffic.
2. **Power**: display active + WCNSS bring-up transient. Compare rail state and
   PMIC PON reason across the two cases (the harness already captures both).
3. An **upstream regression between 6.16 and 6.18** in interconnect/genpd/clock
   handling for MMSS — bisectable now that 6.12 and 6.16 references exist.

Disproof for (1)/(2): a 6.18 image with display active but WCNSS and modem
firmware removed, soaked. If that is stable, the collision is real and the
mechanism is arbitration/power, not the display pipe.
